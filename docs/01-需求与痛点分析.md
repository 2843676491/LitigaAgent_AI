# 一、项目需求深挖（对应第 1 步）

> 项目：合同争议模拟庭审多 Agent 推演系统（LegalCourt AI）
> 定位：企业法务 / 律所内部的**争议预判与举证演练工具**，不是对外出具法律意见的产品。

## 1.1 从"一句话需求"拆到可执行定义

原始表述只有一句：*输入争议事实 + 合同条款，多个角色 Agent 模拟庭审流程，双方举证、交叉质询，法官 Agent 归纳争议焦点并给出风险等级与倾向性意见，最后由法务人工复核落地。*

把它拆成 6 个必须回答的问题，才能变成工程需求：

| 问题 | 结论（本项目的定义） | 为什么必须定义 |
|---|---|---|
| 谁在用 | 企业法务（主）、外部律师（次）、合规/风控（查审计） | 决定权限模型与输出格式（内部意见书 vs 对外文书） |
| 什么时候用 | 合同签署前的条款风险预判；纠纷已发生但未起诉时的胜负预判 | 决定输入是"条款"还是"条款+事实+证据" |
| 输入到底是什么 | ①合同文本（PDF/DOCX/MD）②争议事实陈述（自由文本）③可选：己方证据清单 | 输入边界决定解析、切片、检索策略 |
| 输出到底是什么 | 结构化《争议推演意见书》：争议焦点清单、双方论点、证据引用、风险等级、倾向性意见、补强建议、置信度 | 输出不定结构化，就无法评测、无法入库、无法复核 |
| 什么叫"推演成功" | ①每条论点有可溯源引用 ②焦点识别覆盖人工标注 ③无证据不下定性结论 ④高风险/低置信度必须人工复核 | 这是验收标准，也是评测集的标注依据 |
| 什么不做 | 不做法律建议的最终效力背书；不替代律师；不生成对外起诉状/答辩状 | 划边界，避免合规越界 |

## 1.2 需求的三个层次

**表层需求（用户说出来的）**
- 多个 Agent 辩论、法官裁决、结果可溯源、人工复核。

**真实业务需求（用户没说但必然要）**
- *可解释*：法务拿着意见书去见业务方/老板，必须能指出"依据是《民法典》第 585 条 + 类案（2021）京 03 民终 xxxx 号"。
- *可复核*：结论错了要能追到哪一步错——是检索漏了，还是 Agent 编了。所以要**全链路审计**与**证据快照**。
- *可收敛*：辩论必须有终点，否则法务等不起，也付不起 token。
- *可控成本*：一次推演的模型调用次数要可预算（轮次上限 + 每轮检索次数上限）。
- *不偏置*：原告/被告必须"武器对等"，否则推演结论就是预设结论。

**隐含需求（工程上不做就会崩）**
- 文档去重与版本管理（同一份合同反复上传不能污染证据库）。
- 条款级切片：合同是"条"为单位的，按 512 token 无脑切会把"第 7 条 付款条件"和"第 8 条 违约责任"切碎，导致引用错位。
- 证据效力分级：法条 > 司法解释 > 类案 > 解释性材料，冲突时必须按层级取舍，而不是"谁的分数高听谁的"。
- 结构化输出的 Schema 校验：LLM 输出必须过 JSON Schema，否则前端/入库全挂。
- 降级路径：检索为空、模型超时、Schema 不合法时的兜底，而不是 500。

## 1.3 角色与用例（谁触发、谁消费）

| 角色 | 权限 | 典型动作 |
|---|---|---|
| 法务专员 `lawyer` | 建案、上传、发起推演、读自己的案件 | 上传采购合同 + 写争议事实 → 发起推演 |
| 复核人 `reviewer` | 读全部案件、复核 HITL、签署意见 | 看到"高风险管理待复核"→ 确认/驳回并写理由 |
| 合规/审计 `auditor` | 只读审计日志与链路校验 | 抽查某次推演的证据来源与复核人 |
| 管理员 `admin` | 用户与语料库维护 | 更新法条库、类案库版本 |

## 1.4 验收标准（写进测试与评测集的硬指标）

1. **溯源率 100%**：意见书里每个 `claim` 至少 1 个 `evidence_id`，且 evidence 能在语料库中查到原文。
2. **零无证定性**：无证据支撑时，结论只能是 `undetermined`，不得输出"构成违约/应当赔偿"。
3. **焦点覆盖率 ≥ 0.8**：与人工标注的争议焦点集合相比。
4. **收敛可控**：任意输入下轮次 ≤ `MAX_ROUNDS`（默认 3），且必然终止。
5. **HITL 命中**：置信度 < 0.72 或存在证据冲突或风险等级=高 → 必须暂停等人工。
6. **审计链可验**：`verify_chain` 对任意时间点重算哈希一致，篡改可被发现。
7. **端到端 P95 < 8s**（Mock LLM 本地基准；真实模型另计）。

# 二、项目痛点分析（对应第 2 步）

痛点不是"功能缺失"，而是**这个场景里天然会出错的地方**。下面每条都给出"现象 → 根因 → 系统解法 → 可验收指标"。

## 痛点 1：单模型给结论 = 有偏见的结论

- **现象**：法务把合同和事实喂给一个模型，问"我方能不能赢"，模型往往顺着提问者的立场写，还会补出并不存在的判例。
- **根因**：单次生成没有对抗压力，也没有"必须举证"的约束；立场由 prompt 决定，不由证据决定。
- **解法**：拆成**目标对立**的两个 Agent（主张/抗辩），二者工具权限与上下文对称；法官 Agent 只做**证据强度比较**，不做自由生成；且所有结论强制挂 `evidence_id`，无证据即 `undetermined`。
- **验收**：`no_evidence_verdict_rate = 0`；主张证据支撑率 ≥ 0.9。

## 痛点 2：辩论不收敛 / 无限循环

- **现象**：双方 Agent 互相"你举证不足→你也没举证"，轮次无限，token 烧穿。
- **根因**：Agent 没有终止判据，只有"继续生成"的默认行为。
- **解法**：三层收敛控制：①`max_rounds` 硬上限；②每轮必须有**新增信息**（新证据/新焦点）才允许进入下一轮，否则判为"重复质询"强制收敛；③法官给出 `converged` 与 `convergence_reason`，由图的**条件边**决定是否回到辩论节点。
- **验收**：`avg_rounds ≤ 3`、`max_rounds_terminated = True`（用"双方互喷"的对抗性输入做压测）。

## 痛点 3：证据冲突无处置规则

- **现象**：原告引《民法典》第 585 条说违约金可调减，被告引同一司法解释的另一条说应尊重约定，两条都"相关"，模型取平均，结论糊掉。
- **根因**：检索只给相关性，不给**效力层级**；没有冲突登记机制。
- **解法**：`authority_tier`（法条 1 / 司法解释 2 / 类案 3 / 解释材料 4）+ **冲突登记表**（同一焦点下 tier 相同但结论相反的引用对）+ 仲裁规则：高层级优先；同层级则按"事实贴合度"（关键词与事实的重合度）取舍；无法取舍时**降级为 `undetermined` 并标记 `conflict`**。
- **验收**：`conflict_flagged_accuracy ≥ 0.85`；冲突未解决时输出必含 `undetermined`。

## 痛点 4：检索质量决定一切，而法律检索是"精确匹配 + 语义"混合体

- **现象**：纯向量检索会把"违约金过高"召回成一堆"违约金"泛泛条款；纯 BM25 抓不到"约定解除权"与"法定解除权"的同义关系。
- **根因**：法条短、术语密度高，向量模型对条文编号和术语缩写不敏感；BM25 对改写不敏感。
- **解法**：Milvus 向量 + BM25 双路召回 → RRF 融合（k=60）→ 规则重排（层级 + 词面重合 + 条款号命中）。法条按**条**切片，类案按**裁判要旨**切片，检索结果带 `article_no` 与 `case_no` 便于精确命中。
- **验收**：`recall@5(statute) ≥ 0.85`、`recall@5(case) ≥ 0.8`、`MRR ≥ 0.7`。

## 痛点 5：人工复核被形式化

- **现象**：系统每次都说"请人工复核"，法务直接点"通过"，复核变成橡皮章，合规审计时无法证明"人真的看过"。
- **根因**：复核节点没有**触发条件**、没有**必看项**、没有**差异化信息**。
- **解法**：HITL 只在 `confidence < 0.72 || has_conflict || risk_level == 高` 时触发；复核界面强制展示"待确认的 3 个关键判断 + 冲突项 + 缺失条款"；复核必须给出 `decision` 与 `comment`（拒绝时 comment 必填）；复核动作写审计（含 `reviewer`、`ts`、`opinion_hash`）。
- **验收**：`hitl_trigger_rate` 落在 20%~60% 区间（太低=没把关，太高=模型不可用）；`review_reject_requires_comment = True`。

## 痛点 6：合同条款与事实"对不上号"

- **现象**：意见书说"依第 8 条应支付违约金"，但合同第 8 条其实是"争议解决"，引用错位，法务当场失去信任。
- **根因**：切片丢失条款号、检索只回文本不回定位。
- **解法**：切片时保留 `clause_no`、`offset`、`raw_text`；证据对象必须带 `locator`（`contract#第8条` 或 `statute#民法典第585条`）；**引用校验节点**在 `finalize` 前逐条核对 evidence 是否存在于索引，不存在则剔除并降置信度。
- **验收**：`citation_validity_rate = 1.0`（引用的每条证据都能在索引中定位到原文）。

## 痛点 7：成本与延迟不可控

- **现象**：一次推演 30+ 次模型调用，法务等 40 秒，产品没法上线。
- **根因**：每轮每 Agent 各自检索、各自生成，无缓存、无预算。
- **解法**：检索结果按 `(query_hash, top_k)` 缓存（Redis 语义，本地用 LRU 实现）；编排器设 `max_llm_calls` 预算与超时；法官只读双方论点不重复生成；SSE 流式把等待变成"可见进度"。
- **验收**：`p95_latency < 8s`（Mock）、`llm_calls_per_hearing ≤ 12`。

## 痛点 8：权限与数据边界（企业落地必问）

- **现象**：案件含商业机密，A 部门法务能看到 B 部门案件；审计只记"某人调了接口"。
- **根因**：只有认证没有授权；审计粒度太粗。
- **解法**：RBAC（角色→权限）+ ABAC（`case.owner_dept == principal.dept` 或 `principal.role in {auditor, admin}`）；审计记录到**动作级**（节点、工具、入参摘要、出参哈希、操作人、时间、前后哈希）。
- **验收**：越权访问返回 403 且写审计；`audit_chain_integrity = True`。
