# 三～七、流程拆解、难点、重构与闭环

## 3. 把复杂项目拆成流程（第 3 步）

拆解原则：**按"状态变化"拆，不按"功能模块"拆**。每个阶段必须是可观测、可落库、可重放的一步，否则审计就断链。

| 阶段 | 名称 | 输入 | 动作 | 输出（落库对象） | 失败分支 |
|---|---|---|---|---|---|
| P0 | 接入与鉴权 | 上传合同 + 事实文本 + 身份 | RBAC/ABAC 判定、限流 | `case` 记录 | 403/413 → 审计 |
| P1 | 文档治理 | 原件 | 解析（MD/TXT/PDF 文本层）、**MD5 去重**、原件存 MinIO（本地为对象目录） | `document` + `raw_store_path` | 解析失败 → 提示人工转文本 |
| P2 | 条款级切片 | 合同全文 | 按 `第X条` / 编号项切片，保留 `clause_no/offset/raw` | `chunk` 列表（含 md5） | 无条款结构 → 段落回退切片 |
| P3 | 意图路由 | 事实 + 案件元信息 | Orchestrator 判定 `dispute_simulation / contract_review / statute_consult` | `route` 字段 | 低置信 → 默认走 `contract_review` |
| P4 | 混合检索 | 检索 query（来自焦点/主张/条款） | 向量 + BM25 双路 → RRF → 重排 → 证据分级 | `evidence[]`（带 locator/tier/score） | 空召回 → 标记 `insufficient_evidence` |
| P5 | 主张构建 | 证据 + 事实 | 原告 Agent 输出论点清单（每条挂 evidence_id） | `argument[]` | 无证据 → 论点标记 `undetermined` |
| P6 | 抗辩与交叉质询 | 对方论点 + 己方证据 | 被告 Agent 逐条反驳 + 弱点攻击 + 反证 | `rebuttal[]` | 同上 |
| P7 | 裁决与收敛 | 双方论点 + 冲突表 | 法官 Agent 归纳焦点、比对强度、判风险、给倾向意见、判 `converged` | `opinion`（JSON Schema） | 不合法 → 重试 1 次，仍失败降级为"待人工" |
| P8 | 复核与归档 | opinion + 置信度/冲突/风险 | HITL 闸门（条件触发）→ 人工确认 → 签署 → 审计 | `hitl` + `opinion(final)` + `audit` | 拒绝 → 回到 P5/P6 重推（带复核意见） |

> 关键：P7 与 P5/P6 之间是**环**（条件边），不是直线。P8 是**可选的阻塞点**（`interrupt`），不是终点。

## 4. 项目难点（第 4 步）

难点 = "工程上一定会失败的地方"，与痛点一一对应但更具体：

**D1 状态机与循环控制**：多 Agent 辩论是有环图，LangGraph 里必须显式定义条件边与轮次计数，否则 `recursion_limit` 兜底报错；且暂停/恢复要求状态可序列化（`TypedDict` 只放可 JSON 化的东西，不放 client 对象）。

**D2 证据对象的一致性**：检索出的证据必须与"引用它的人"共享同一个 `evidence_id` 空间，否则法官无法比较双方证据强弱。→ 证据表在 P4 统一生成，后续只引用 id，不复制文本。

**D3 对称性（防偏置）**：主张/抗辩两个 Agent 若 prompt、工具、检索配额不一致，结论天然偏。→ 用**同一套 prompt 模板 + 同一组工具 + 同一 top_k**，仅 `side` 变量不同；法官不看"谁说的"，只看"证据强度"。

**D4 引用校验**：LLM 会编造条文号。→ P8 前插入 `cite_guard`：逐条 evidence 回查索引，缺失即剔除 + 降置信 + 审计。

**D5 收敛判据**：仅靠 `max_rounds` 会导致"该多辩的没辩完、该停的停不下"。→ 三重判据（轮次上限 + 新增信息 + 法官 `converged`）。

**D6 HITL 的幂等与并发**：复核接口被点两次、两人同时复核。→ 复核记录带 `status` 状态机（`pending→approved/rejected`），二次提交返回 409；`thread_id` 与 `hearing_id` 一对一。

**D7 检索质量与切片粒度耦合**：条款切太细丢上下文，切太粗引用不精确。→ 双粒度：`chunk`（条款级，用于引用）+ `parent_text`（前后各一条，用于生成时补上下文）。

**D8 评测闭环**：没有标注集就没有"改好了"的证据。→ 建 10 条标注用例（期望法条、期望焦点、期望风险等级），每次改切片/召回策略都跑 `run_eval.py` 出 14 项指标。

## 5. 依据难点重构后的流程（第 5 步）

第一版直线流程有 4 个结构性缺陷，重构如下：

| 原设计 | 问题 | 重构后 |
|---|---|---|
| 检索在"原告 Agent 内部"做 | 被告检索不到同一批证据，无法比较强弱；也无法审计"谁查了什么" | 抽成**共享 `retrieve` 节点**，证据入库后双方只按 id 引用（解 D2） |
| 只有一个 `judge` 节点出结论 | 编造条文无人拦截 | 插入 **`cite_guard`** 节点（P7.5），校验不过则降置信并触发 HITL（解 D4） |
| 辩论用 `while` 直到"满意" | 无界 | 引入 **`convergence` 控制器**：`round < max_rounds` 且 `last_round_new_info > 0` 且 `not judge.converged` 才继续（解 D5） |
| HITL 在最后"提示一下" | 变成橡皮章 | HITL 升级为 **graph 内的 `interrupt` 节点**：真暂停、状态持久化、必须带 `decision+comment` 才能恢复（解 D6） |
| 双方 prompt 各自写 | 偏置 | 统一 `build_side_prompt(side)`，参数化差异仅 `side/task`（解 D3） |

新增/调整后的节点序列：

```
START → ingest(P1+P2) → orchestrate(P3) ─┬─ consult ─→ retrieve → consult_answer → END
                                        ├─ review  ─→ retrieve → clause_risk → hitl? → finalize → END
                                        └─ dispute ─→ retrieve → plaintiff → defendant → judge
                                                                        ↑              │
                                                                        └── continue ───┤ (round<max & new_info>0 & !converged)
                                                                                       └─ stop → cite_guard → hitl? → finalize → END
```

## 6. 串联成业务闭环（第 6 步）

**主链路（一次推演的完整闭环）**

```
建案(P0) → 治理(P1/P2) → 路由(P3) → 检索(P4) → 主张(P5) → 抗辩(P6) → 裁决+收敛(P7)
      → 引用校验(P7.5) → 人工复核(P8) → 签署归档 → 审计留痕 → 评测回流
```

**状态机（hearing 生命周期）**

| 状态 | 触发 | 出口 |
|---|---|---|
| `created` | 建案 | 发起推演 |
| `running` | 图执行中 | `awaiting_review` / `completed` / `failed` |
| `awaiting_review` | interrupt 命中 | 复核通过 → `completed`；拒绝 → 带意见回炉 `running` |
| `completed` | finalize | 只读、可导出 |
| `failed` | 异常/预算超限 | 审计留痕，可重试 |

**数据闭环（这是"能迭代"的关键）**

1. 每次推演落 `state_json` 快照 + `audit` 链 → 可重放。
2. `run_eval.py` 跑标注集 → 出 14 项指标 → 定位 badcase（召回漏了哪条法条 / 焦点识别漏了哪个）。
3. badcase → 调整切片粒度、RRF 权重、rerank 规则、prompt 约束 → 重跑评测对比。
4. 法务复核结论（通过/驳回 + 理由）反哺标注集，形成**人工标注 → 评测 → 优化**的闭环。

## 7. 流程自检（第 7 步：需求/痛点 → 流程，找漏洞并改）

用"需求 × 流程"做交叉检查，发现 5 个漏洞并已修正：

| # | 发现的漏洞 | 影响的痛点 | 修正 |
|---|---|---|---|
| 1 | P2 只做条款切片，**没有把"事实"切片入索引**，导致"逾期 45 天"这类事实无法被检索命中 | 痛点 4 检索质量 | 事实文本单独成 `facts` 证据（tier=4），参与检索但**不可作为定性依据**（只做上下文） |
| 2 | P3 路由低置信时"默认 review"，但**争议推演才是最贵的路径**，误路由会浪费预算 | 痛点 7 成本 | 路由低置信时先走 `retrieve` 取 top3 证据做**二次判定**，再定路径 |
| 3 | P7 的 `risk_level` 只按"证据强度差"算，**忽略了合同本身缺失关键条款**（缺付款条件/缺违约责任），这正是企业最高频的真实风险 | 痛点 1、6 | 增加 `missing_clause_check`：对照条款清单检查 12 类必备条款，缺失即升风险等级并列入补强建议 |
| 4 | P8 复核拒绝后"回炉"，但没有限制**回炉次数**，可能死循环 | 痛点 2 | `revision_count ≤ 2`，超限强制转人工线下处理 |
| 5 | 审计只记节点，**没记"这次推演花了多少 token/调用"**，成本不可复盘 | 痛点 7 | 审计字段增加 `llm_calls`、`tokens_in/out`、`latency_ms` |

**结论**：流程闭合，无"只进不出"的环节；每个阶段都有失败分支与落库对象；环有界（轮次 + 回炉次数双上限）；阻塞点只在 HITL。
