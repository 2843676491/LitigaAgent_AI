# 五、面试追问准备

> 用法：先背「30 秒版本」，再按问题逐条过。每条都写清 **机制 → 代码位置 → 实测数字 → 追问反制**，避免只讲概念。
> 对应实现：`src/legalcourt/graph/nodes.py`、`rag/hybrid.py`、`audit.py`、`eval/metrics.py`。

## 0. 30 秒版本

我做了一个合同争议的模拟庭审系统：输入争议事实和合同，原告、被告两个目标对立的 Agent 各自检索法条和类案、多轮互相攻击，法官 Agent 归纳争议焦点、比对证据强度、按效力层级处理冲突，最后给风险等级和倾向性意见；关键结论会暂停等法务签署，全链路写哈希链审计。
核心不是"多几个 Agent"，而是**把不可靠的部分（论证）交给模型，把可校验的部分（强度、风险、收敛、引用）压成代码**，所以能跑评测、能回归。

---

## 1. 怎么防止双方 Agent 无限辩论？

**一句话**：三重收敛 + 双层上限，实测平均 1.75 轮、最多 3 轮。

展开：
1. **轮次上限**：`MAX_ROUNDS=3`，`judge` 里 `round >= max_rounds` 直接收敛，理由写明"达到轮次上限"。
2. **信息增量判据**：第 2 轮起，若本轮双方都没有引入新 `evidence_id`（`new_evidence_count == 0`），说明继续吵也不产生新信息 → 收敛。
3. **强度差收敛**：相邻两轮的平均强度差变化 `< 0.05` 且没有未决焦点 → 收敛。
4. **图层面兜底**：`recursion_limit=40`，防止边写错导致真死循环；`MAX_REVISIONS=2` 限制复核驳回后的回炉次数。
5. **成本上限**：`LLM_MAX_CALLS_PER_HEARING=14`，Mock 实测 6.4 次/案。

追问「如果第 2 轮又检索到新证据怎么办？」→ 让它继续，但新证据进入全局 evidence 池后会被后续轮复用，通常第 3 轮就无新增；若到上限仍未收敛，输出会标 `converged=false` 并写明"未收敛"，交人工，而不是假装有结论。

## 2. 证据互相冲突怎么处理？

**一句话**：先分级，再判是否"同层级对立"，能按效力层级取舍就取舍，不能就标未决转人工。

展开：
- **分级**：`AUTHORITY_TIER`：法条 1 > 司法解释 2 > 类案 3 > 合同条款 4 > 事实陈述 5。强度分 `(5-tier)/4`，天然让高层级证据更"重"。
- **冲突定义**：同一焦点下，原告引用了 `favor=plaintiff` 的类案，被告引用了 `favor=defendant` 的类案 → 同层级结论相反，记 `ConflictRecord`。类案语料每条都带 `favor` 字段，这是冲突能被机器识别的前提。
- **处置三分支**：焦点内存在 tier≤2 的依据 → `higher_tier`（写明"存在更高层级依据"）；否则 `unresolved` → 焦点状态置 `conflict`、整体倾向置 `undetermined`，并强制命中 HITL。
- **不装作没冲突**：冲突会原样写进意见书和前端，两个证据 id 都可点击回原文。
- **审计**：`judge.verdict` 里记录冲突数量与处置结果，事后可复核"当时凭什么这么取舍"。

追问「法条和类案冲突呢？」→ 目前语料里法条是规则、类案是适用，规则优先是法律解释的基本秩序；如果是"法条之间"冲突（新法优于旧法、特别法优于一般法），当前没做，属于已知短板，生产要接法规版本库。

## 3. 怎么避免模型偏置？

**一句话**：对称输入、对称工具、证据强制、无证据不定性，四道锁。

1. **对称 Prompt**：主张/抗辩共用一份模板，只换 `side` 参数；不给任何一方额外的事实摘要或"参考答案"。
2. **对称工具权限**：双方都只能调 `retrieve`（同一个检索器、同样 top_k、同样语料），不存在"一方能查最高法内部库"。
3. **证据强制**：`Argument.basis` 必须是被检索到的 `evidence_id`；`cite_guard` 落库前逐条 `index.exists()`，无效引用剔除，并把置信度按剔除比例下调。
4. **无证据不下定性**：焦点一方强度为 0 → `undetermined`；整体 `undetermined=True` 时意见书不给倾向。评测里 `no_evidence_verdict_rate=0.00` 是硬红线。
5. **可观测**：每案输出双方强度对比条，偏置会以"某方永远 1.0、另一方 0"的形式暴露，评测集能抓到。

追问「法官 Agent 自己会不会偏？」→ 会，所以法官不自由裁量：强度、风险、置信、倾向都是代码算的（`judge` 节点里的公式），LLM 只负责措辞（焦点标题、观点摘要、补强建议）。这叫"把裁决权从模型手里拿走"。

## 4. 对抗式 Agent 和普通客服多 Agent 有什么区别？

| 维度 | 客服多 Agent | 本项目 |
|---|---|---|
| 目标关系 | 分工互补（查订单/查物流/回复） | **目标对立**（主张 vs 抗辩） |
| 收敛方式 | 任务完成即结束 | 需要**仲裁层**按证据强度与效力层级收敛 |
| 失败模式 | 答错、答慢 | **不收敛、偏置、无证据定性** |
| 评测口径 | 解决率、满意度 | 召回、引用有效、焦点覆盖、复核率 |
| 状态 | 无状态或短会话 | 长事务：`interrupt` 暂停、跨进程恢复 |

一句话总结：客服是**并行分工**，对抗是**互相证伪**；前者靠路由，后者靠仲裁。

追问「那不就是两个 prompt 互喷？」→ 不是：双方共享同一个证据池和同一套检索，论点必须挂证据 id；仲裁层用的是可计算的强度/层级/冲突规则，而不是让第三个模型"感觉谁对"。

## 5. HITL 的幂等与并发怎么做？

**一句话**：状态机 + 图内 interrupt + 数据库状态校验，重复提交返回 409。

- **暂停**：`hitl_gate` 里 `interrupt(payload)`，LangGraph 把状态写进 `SqliteSaver`（`thread_id=hearing_id`），进程重启也能恢复。
- **恢复**：`Command(resume={decision, reviewer, comment})`；`interrupt` 之前的代码**只做纯计算、不写库**，因为恢复时节点会重放。
- **幂等**：`POST /hearings/{id}/hitl` 先查 `status`，不是 `awaiting_review` 直接 409（已被别人处理/已归档）；`db.add_hitl` 记录每次决定。
- **驳回闭环**：`reject` 必须填理由（Pydantic `field_validator`，空理由 422）；`revision_count + 1`，`<=2` 才回 `plaintiff` 重跑，否则强制 `finalize` 并标"复核未通过"。
- **审计**：`hitl.pending / hitl.approve / hitl.reject / hitl.auto_approved` 四类动作分别留痕。

追问「两个人同时点通过？」→ 第一个请求把状态改为 completed，第二个读到非 awaiting → 409；即便并发穿过检查，图状态已结束，`Command(resume)` 也不会产生第二次裁决。

## 6. 引用校验具体怎么做？能防幻觉吗？

- 证据统一编号：法条 `S-xxx`、司法解释 `J-xxx`、类案 `C-xxx`、合同切片 `CT-{case6}-Cxx`、事实 `FACT-{case6}`。
- `cite_guard` 校验三件事：id 是否存在、证据是否属于本案允许的范围（文档级隔离）、引用是否出现在对应焦点的 basis 里。
- 无效引用：从 `citations` 和论点 basis 中剔除，`confidence -= 0.15 * 剔除比例`，审计记 `cite_guard.drop`。
- 前端每条引用可点开看 `locator` 与原文片段，法官结论里的每个数字都能回溯。

**能防住"编造条文号"，防不住"引用了真法条但理解错"**——后者要靠人工复核与评测集里的"焦点/风险一致率"来兜。这点要如实说。

## 7. 评测口径为什么不用 LLM 打分？

- LLM 打分不可复现：同一条数据两次打分可能不同，无法判断"改一版是变好还是变坏"。
- 所以 14 项指标全部从 state 里取**结构化中间产物**：证据列表（算 Recall/MRR）、论点 basis（算支撑率）、焦点集合（对比标注）、冲突（对比"是否存在相反类案"）、引用（逐个 exists）、轮次/调用数/延迟、审计链。
- 红线三条：`citation_validity=1.00`、`no_evidence_verdict_rate=0.00`、`audit_chain_ok`。任何版本回退必须先过红线。
- Bad case 闭环：跑评测 → 定位是切片、召回还是裁决规则 → 改一处 → 重跑同一集，看指标动的是不是预期那一项。

追问「8 条够吗？」→ 不够，只够做机制回归，不够做统计显著性；生产要 200+ 条并按争议类型分层。这是已知短板，不吹。

## 8. 为什么用 LangGraph，而不是自己写 while 循环？

- 需要**有环**（judge 不收敛回 plaintiff）和**条件边**（路由/收敛/复核三处分支），手写 while 很快变成状态散落各处的意大利面。
- 需要**持久化暂停**：`interrupt` + Checkpointer 是原生的，等价实现要自己写"存档-退出-恢复"。
- 需要**可观测**：`stream_mode="updates"` 直接给出"哪个节点产出了什么"，SSE 逐节点推送零改造。
- 代价：版本耦合（锁定 `langgraph==1.2.20`）、调试链路长；所以把业务逻辑全部放在纯函数节点里，图只负责连接，换编排框架时业务不动。

## 9. 为什么用 RRF 而不是加权求和？为什么不用 Cross-Encoder 重排？

- 向量分是余弦相似度，BM25 分是无界实数，量纲不同；加权求和要归一化 + 调权，换 embedding 模型后权重全废。RRF 只用排名，`k=60` 是经验值，稳定。
- 重排用规则：`0.55*RRF + 0.30*词面重合 + 0.10*效力层级 + 0.05*条文号命中`。单机无 GPU，Cross-Encoder 延迟不可接受；规则版可解释、可单测。生产有 GPU 再换 BGE Reranker，接口不变。

## 10. 这套系统能替代律师吗？边界在哪？

不能，也不该。它替代的是**准备工作**：查法条、找类案、列焦点、标冲突、写初稿、留痕。
三条硬边界写在产品里：无证据不定性、关键结论必须人工签署、输出明确标注"推演材料不构成法律意见"。
真正有价值的是"把法务从 3 小时的材料整理压到 20 分钟复核"，而不是"让模型判案"。

## 11. 如果重做，你会先改什么？

1. **检索**：先上 BGE-M3 语义向量 + 扩法条库，法条召回 0.60 是当前最大短板。
2. **焦点数量**：现在固定最多 5 个，精确率被稀释到 0.45；改成"证据支撑度阈值 + 动态条数"。
3. **事实入证**：现在事实只作上下文、不进索引，导致"有法条无事实"也能算出强度；应把事实切片成 `FACT-xxx` 并参与强度计算（需先解决"自证"问题）。
4. **评测集**：8 条扩到 200+，按争议类型分层，才能谈统计意义上的提升。

> 面试时主动说短板，比被问出来强；但要说清"我知道它为什么低、下一步动哪里、动了看哪个指标"。
